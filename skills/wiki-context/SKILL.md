# Wiki 长期认知记忆系统与持久化准则

## 核心架构原则与两层分工

```text
                 AGENTS.md（人类层：宪法级行为准则、交互人格、底线）
                     |
        Agent记忆总结.md（Agent层：四段式高密度索引卡：“我应该如何理解这个用户”）
              |
              ↓
        ┌───────────┐
        │           │
      Wiki  ←→  Session（双向链接：Wiki负责“现在是什么”，Session负责“为什么变成这样”）
        │           │
        └───────────┘
```

1. **人类层（静态底座）**：
   - `AGENTS.md`：全局行为准则与纪律约束（宪法级静态基准，行为规则严禁写进 Wiki）；
   - Wiki 词条：`Self.md`（个人情况与画像）、`Topics/*.md`（活跃项目演化与决策）、`待整理/*.md`（未整理线索），沉淀客观事实、当前定案与核心方案。

2. **Agent 记忆层（动态追溯）**：
   - **Agent 记忆总结 (`Agent记忆总结.md`)**：放在 Wiki 根目录下，严格采用四段式高密度结构（当前阶段 / 用户特点 / 长期项目 / 最近变化），字数收敛在 800~1000 字内，回答“我应该如何理解这个用户”。
   - **物理会话日志与证据库 (`~/.dsh/sessions/`)**：Session 是证据库而非上下文库，记录真实历史交互细节与决策论证推导，严禁全量注水。

3. **默认自主落盘与就地纠错**：
   - 无需人工提案审批流程。只要识别到用户的个人情况变动、偏好倾向、方案推翻或跨会话断点，Agent 均有权自主判断并直接调用 `wiki_write` 落盘，不询问用户、不口播提案编号；
   - 认知允许随交互深入不断修正。遇到更新或推翻的事实时，就地覆写更新，不堆叠历史矛盾。

## 召回策略（Recall Strategy）

**核心铁律：Session 是证据库，不是上下文库，严禁全量注水。**

### 三层召回优先级原则
1. **第一层：Wiki / Agent记忆总结（先看已整理信息）**
   - 优先通过上下文已注入的记忆档案、`Agent记忆总结.md` 或调用 `wiki_search` / `wiki_read` 获取已整理认知。
   - **已有定案直接回答，严禁无端调用 `wiki_recall_session`**。
2. **第二层：关联 Session Recall（定向追溯决策细节）**
   - 当 Wiki 词条或记忆总结中缺少具体的决策细节、推导证据、代码片段或特定会话上下文时，依据双向链接中登记的 `topic`、`wikiRef` 或关联词，定向反查并调用 `wiki_recall_session` 提取对应会话切片。
3. **第三层：全局搜索（无明确关联时的兜底检索）**
   - 在既没有命中词条定案、也没有找到双向链接关联时，按检索四维度（关键词/时间范围/工作区）在底层物理日志中做全局搜索。

### 检索四维度契约
调用 `wiki_recall_session` 时组合使用以下四维度：
- **维度 1：主题定向反查 (`topic`)**：如 "DSH工作台"、"2026公考"、"memory"，系统通过双向链接索引自动反查关联 Session ID，点对点毫秒级抽取。
- **维度 2：会话精准定位 (`sessionId`)**：直接指定特定会话 ID 精准定位解压，零遍历开销。
- **维度 3：多关键词匹配 (`keywords` / `query`)**：支持传入多个关联词数组（如 `['memory', '上下文', 'recall']`），命中任一词即可（OR 逻辑）。
- **维度 4：时空剪枝 (`since` / `until` / `workspace`)**：利用时间戳/日期边界与工作区名称剪枝 90% 以上无关目录，保障极端场景下的性能稳定。

### 输出格式规范
`wiki_recall_session` 严格输出紧凑单轮证据，单段助言截断在 300~500 字内：
```text
来源：<YYYY-MM-DD HH:mm:ss> session_<sessionId> (工作区: <workspace>)
关联Wiki: <topics/wikiRefs...>
上下文：
用户：<用户问题>
回答：<最终结论 (300~500字截断)>
```

## 双向链接（Bidirectional Link）

### Wiki ↔ Session 数据职责正交
- **Wiki 负责“现在是什么”**：当前处于什么阶段、最新核心方案是什么、确立了哪些定案、推翻了哪些设计；
- **Session 负责“为什么变成这样”**：当时因为什么原因发生争论、具体的排查日志细节、用户当时的原话与决策权衡过程。

### 双向链接索引维护与使用
- **索引位置**：在 `.wiki/session-links.json` 中统一轻量维护映射关系：
  ```json
  {
    "session-exam-001": {
      "sessionId": "session-exam-001",
      "workspace": "申论系统课",
      "topics": ["2026公考"],
      "wikiRefs": ["Topics/2026公考.md"],
      "updatedAt": "2026-10-09T09:00:00.000Z"
    }
  }
  ```
- **写入登记**：当在某个会话中通过 `wiki_write` 沉淀认知时，传入当前 `sessionId` 参数，系统自动建立该会话与对应 Wiki 词条及主题的双向关联。
- **反查闭环**：在需要追溯“为什么变成这样”时，通过 `topic` 或 `wikiRef` 即可秒级反向穿透到真实物理会话证据。

## 适用场景与四工具面契约

1. **词条检索与查阅 (`wiki_search` / `wiki_read`)**：
   - 当任务涉及用户长期背景、历史项目演化、私有偏好或过往技术决策时，调用 `wiki_search` 检索索引，或通过 `wiki_read` 定向读取指定章节/大纲。
   - 隐式利用历史认知指导行动，严禁在回答中输出“根据知识库/你之前提到过”等元废话。

2. **历史会话物理召回 (`wiki_recall_session`)**：
   - 遵循上述三层召回优先级原则，仅在缺乏决策细节证据时调用；
   - 严格按单轮紧凑格式抽取（用户真实问题 + 助手 300~500 字结论摘要），严禁全量长文本注水。

3. **认知写入与就地迭代 (`wiki_write`)**：
   - 严禁将临时调试日志、临时排查猜想、中间推导或瞬态排查垃圾写入 Wiki。
   - 识别到以下认知增量时，Agent 自主判断并主动调用 `wiki_write`：
     - **个人情况更新**：生活状态、健康精力、财务变动、备考/职业进展等（更新至 `Self.md`）。
     - **个人倾向与偏好**：沟通风格、技术偏好、取舍倾向等（更新至 `Self.md` 或对应 Topic）。
     - **项目演化与决策推翻**：活跃项目的核心阶段演进、架构推翻或重大方案取舍（更新至 `Topics/<项目>.md`）。
     - **跨会话交接断点**：未完待续的任务线索、排障遗留事项（更新至根目录 `Agent记忆总结.md`）。
     - **待整理技术构想**：尚不成熟或待整理的技术构想（更新至 `待整理/<主题>.md`）。
   - **双向锚定**：产生确定性认知时传入 `sessionId`，登记会话锚点。
   - **小节更新**：若针对已有词条的特定小节更新，传入 `section` 参数执行**就地替换**，避免重复与自相矛盾；若无对应小节则自动在文末建立。
   - **单篇物理限长（≤4.5KB / ~2000 字）**：保持高密度与纯度。写入时优先提炼核心结论，严禁日志式流水堆砌；详尽历史与大表下沉至 `Archive/详版备查-*.md`。若文件超过 4.5KB 软上限，工具将输出精炼提醒。
   - **四段式结构锁死**：Topic 词条严格围绕四个核心二级标题（当前状态与核心方案 / 演进与调整记录 / 已推翻的设计与决策 / 后续计划）就地维护。
